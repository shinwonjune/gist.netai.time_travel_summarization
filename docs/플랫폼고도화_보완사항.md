## 1. 배경과 목적

현재 프로젝트는 "데이터 생성 → 축적 → 재현 → 추론 → 요약"이 실제로 도는 **end-to-end 파이프라인/프레임워크**다. 그러나 "플랫폼"이라고 부르려면 추가 조건이 필요하다 — 여러 시나리오·데이터가 올라탈 수 있는 공통 기반, 단계 간 명확한 인터페이스, 운영 관점의 검증(확장성·재현성·관측성). 이 문서는 그 격차를 항목별로 정리하고, 각 항목의 완료 판정 기준을 정의한다.

취업 서사 관점: 아래 A~C가 완료되면 "특정 사건 재현 도구"가 아니라 "임의 시나리오를 올릴 수 있는 시공간 분석 플랫폼"이라는 주장이 성립한다. D~H는 그 주장을 면접에서 방어하게 해주는 엔지니어링 근거다.

## 2. 현재 아키텍처 스냅샷 (이미 갖춘 것)

파이프라인 단계별 담당 모듈 (`gist/netai/time_travel_summarization/` 기준):

| 단계 | 모듈 | 상태 |
|------|------|------|
| 합성 데이터 생성 | `automation/generate_episodes.py`, `physics/` | headless end-to-end 검증 완료 (run9) |
| 데이터 레이크 축적 | `storage/` (factory + MinioAdapter + Local), `config.json`의 `lake` 블록 | 동작하나 확장성 미검증 |
| 시공간 재현 | `playback/`, `app/facade.py` | 완료, 케이스 스터디 검증 |
| 캡처/오버레이 | `video_capture/`, `overlay/` | 60fps 결정론 캡처 완료 |
| VLM 학습 | `training/` (swift LoRA 스크립트, METHODOLOGY.md) | **스크립트만 존재, 학습 미완주** |
| VLM 추론·이벤트 처리 | `vlm_client/`, `VLM_server/`, `event_processing/` | 완료 (F1 정량 결과 보유) |
| 요약 재생 | `playback/`, `ui/` | 완료 |

플랫폼 방향으로 이미 확보된 자산:
- **스토리지 추상화**: `storage/factory.py`가 URI scheme(`s3://`, `minio://`, `file://`)으로 어댑터를 선택 — 스토리지 교체 가능한 구조.
- **설정 외부화**: `config.json`이 `${DATA_PATH}`, `${MINIO_BUCKET}` 등 env 변수를 참조. 하드코딩 아님. `config.example.json` 제공.
- **테스트 18개**: `tests/`에 storage/overlay/physics/capture 단위 테스트 + `lake_benchmark.py`, `test_lookup_benchmark.py` 성능 측정 스크립트.
- **재현성 기초**: 에피소드 시딩(sim-time 단일 클럭, 커밋 0c05bab), headless 결정론 캡처.

## 3. 보완 항목

우선순위 순. 각 항목에 "완료 판정" — 이것이 충족되면 그 항목은 닫힌 것.

### A. VLM 학습 단계 완주 — 폐루프 완성 (최우선)

- **현재**: `training/`에 스크립트(`qwen3vl_lora_swift.sh`, `remote_train.sh`, `run_eval.sh`)와 방법론 문서만 있고, 자체 생성 데이터로 학습→평가를 끝까지 돌린 적이 없다. "생성한 데이터로 학습까지 이어진다"는 주장이 현재는 계획 단계.
- **할 일**: `데이터생성_다음세션_플랜.md`의 1~4단계 그대로 — 소량 배치 생성(N=10) → `build_dataset`(60fps → 10Hz 데시메이션) → overfit 게이트(~50클립, train loss≈0) → L40 본학습·평가.
- **완료 판정**: 자체 생성 데이터로 학습한 LoRA의 평가 결과가 precision/recall 분리로 보고되고, 베이스라인(fine-tuning 전 F1 0.263~0.462)과 비교 수치가 존재.

### B. minIO 데이터 레이크 정량 검증

- **현재**: 연동은 동작하지만 지연·처리량이 미측정 (CLAUDE.md 한계 2번). 측정 도구는 이미 일부 존재 — `tests/lake_benchmark.py`, `tests/test_lookup_benchmark.py`.
- **할 일**:
  1. 기존 벤치마크를 확장해 측정 항목 고정: 청크 로드 지연(p50/p99), 재생 중 프리페치 hit율(`config.json`의 `cache_chunks: 4`, `prefetch_ahead: 2` 파라미터별), 원본 데이터 Hz 대비 재현 좌표 갱신 지연.
  2. 결과를 `docs/minIO고도화일지.md`에 수치 표로 기록.
- **완료 판정**: "60초 재생 기준 좌표 갱신 지연 p99 X ms, 프리페치 설정 Y에서 stall 0회" 형태의 수치가 문서에 존재. "원활하다"는 서술이 아니라 숫자.

### C. 씬·데이터 소스 일반화 — 임의 시나리오 온보딩

- **현재**: `generate_episodes.py --stage`가 임의 USD(로컬/Nucleus)를 받지만, 실제 검증은 AI대학원 빌딩 씬 + `--keep-positions` 조합뿐. 랜덤 스폰은 바닥 없는 지점에서 무한낙하(일지 #7-6). `config.json`의 `visibility_groups`/`prim_map`도 현재 씬 구조에 맞춰져 있음.
- **할 일**:
  1. 스폰 지점 레이캐스트 검증(아래 바닥 존재 확인) 추가 → `--keep-positions` 없이도 임의 씬에서 안전 스폰.
  2. 씬별 프로파일 개념 도입: 씬 경로·카메라·visibility_groups·prim_map을 하나의 프로파일 파일로 묶어 `config.json`에서 선택. 새 씬 온보딩 = 프로파일 1개 작성.
  3. 두 번째 씬(간단한 씬이어도 됨)으로 생성→재현→추론 파이프라인 통과 시연.
- **완료 판정**: 코드 수정 없이 프로파일 추가만으로 두 번째 씬에서 에피소드 생성이 성공.

### D. 단계 간 데이터 계약(스키마) 명세

- **현재**: 단계 사이를 흐르는 데이터 포맷(궤적 CSV/parquet 컬럼, 에피소드 출력 구조, 학습 데이터셋 포맷, 이벤트 목록 JSON `{타임스탬프: [객체ID]}`)이 코드에 암묵적으로만 존재. "플랫폼"은 이 경계가 문서화된 계약이어야 다른 생산자/소비자가 붙을 수 있다.
- **할 일**: `docs/DATA_CONTRACTS.md` 1개 작성 — 각 경계별로 포맷, 필수 필드, 좌표계·시간 기준(어느 클럭인지), 버전. 스키마 변경 시 이 문서를 갱신하는 규칙 명시.
- **완료 판정**: 파이프라인의 모든 단계 경계(최소 4개: 궤적, 에피소드, 데이터셋, 이벤트 목록)가 문서화되고, manifest에 스키마 버전 필드 존재.

### E. 실행 표면 정리 — in-process에서 서비스 경계로

- **현재**: 전부 Kit extension in-process 실행. headless 자동화(`generate_episodes.py --exec`)가 사실상 유일한 프로그래밍 인터페이스. REST/API 계층 없음.
- **할 일 (단계적, 과투자 주의)**:
  1. *단기*: CLI 표면 정리 — 생성/재현/추론 각 단계를 일관된 CLI 인자 체계로 정돈하고 `Readme.md`에 사용법 명시. 이것만으로 "배치 API"라 부를 수 있다.
  2. *장기*: 자연어 질의 표면 — RAG(레이크 카탈로그 검색) + Agentic 오케스트레이션으로 조회·탐지·요약을 자연어 한 문장으로 실행. 상세 설계는 **`agentic_rag_고도화설계.md`** (요청 유형 R1~R7과 route, 단계별 로드맵 포함). REST는 그 하위 구현 세부로 흡수.
- **완료 판정 (단기)**: 새 사용자가 Readme만 보고 3개 단계를 CLI로 실행 가능.

### F. 관측성 — 로깅·메트릭 일원화

- **현재**: 단계별 로그는 있으나(캡처 로그, kit 로그) 파이프라인 관점의 공통 메트릭(단계별 소요시간, 실패율)이 없음. 에피소드당 4.5분 같은 비용 수치가 문서에만 존재.
- **할 일**: 에피소드 manifest에 타이밍(씬 로드, 캡처, 인코딩)과 결과 상태를 기록. B의 벤치마크 결과와 합쳐 "파이프라인 처리량" 수치 확보.
- **완료 판정**: 배치 실행 후 manifest 집계만으로 "에피소드당 생성 비용, 실패율" 산출 가능.

### G. 재현성·버저닝

- **현재**: 에피소드 시드·결정론 캡처는 확보. 그러나 데이터셋·모델에 버전 개념이 없어 "이 모델은 어떤 데이터로 학습했나"를 역추적할 수 없음.
- **할 일**: 데이터셋 빌드 시 소스 에피소드 목록+커밋 해시를 manifest로 기록, 학습 산출물에 데이터셋 버전 태깅. 도구 도입(DVC 등) 없이 manifest 파일 규칙만으로 충분.
- **완료 판정**: 임의의 평가 수치에서 모델→데이터셋→에피소드→생성 커밋까지 역추적 가능.

### I. 멀티유저 동시 이용성 — 토폴로지와 계약 (2026-07-07 추가)

- **목표 토폴로지**: "각자 USD Composer+extension 설치(무거운 클라이언트) + 공유 백엔드(Nucleus·minIO·GPU 서버)". extension은 유일한 얼굴이 아니라 **여러 가능한 클라이언트 중 하나**(CLI, agentic 라우터도 같은 기반을 쓰는 클라이언트)이고, 제어면(extension/CLI) · 실행면(GPU 서버의 잡 러너) · 데이터면(minIO)의 3분리가 뼈대다. L40 원격 생성 검증(2026-07-07, 인증·씬 로드·캡처 전 구간)으로 실행면 분리가 실증됨.
- **Nucleus가 공짜로 주는 층**: 씬(USD)의 동시 열람·공동 편집, 계정별 접근 — "여럿이 같은 빌딩을 본다"는 동시성.
- **우리가 계약으로 만들어야 하는 층** (Nucleus가 해결 안 함):
  1. 레이크 쓰기 경합 — run 네임스페이스 규칙(사용자/날짜 접두어) + "산출물 불변, 버전만 추가"
  2. GPU 잡 스케줄링 — 잡 러너에 큐잉·GPU 배정 (단일 사용자 GPU 경합 사고의 멀티유저 일반화)
  3. 버전 일관성 — 클라이언트(extension) 버전이 달라도 데이터 계약이 지켜지도록 manifest 스키마 버전(D 항목)으로 방어
- **판정 실증**: "동시 사용자 2명이 서로의 산출물을 깨뜨리지 않고 각자 생성→학습을 수행" — 이것이 면접에서 '플랫폼'을 방어하는 가장 강한 시연.

- [ ] 자체 생성 데이터로 학습한 모델의 평가 수치 존재 (A)
- [ ] 데이터 레이크 지연·처리량 수치 존재 (B)

- [ ] 동시 사용자 2명이 서로의 산출물을 깨뜨리지 않고 각자 생성→학습 수행 (I)

### 6-1. 인터랙티브 Capture 버튼 — objectID 오버레이 투영 정합 오차 (2026-07-14 발견, 디퍼)

- **증상**: Time Travel 메인 윈도우의 **Capture 버튼**으로 (재생 모드에서) 캡처하면 objectID 마커가 astronaut 위치와 **일정 비율로 어긋난다**(화면 중심 기준 radial 스케일 오차, "초창기 projection 부정확" 느낌). 시간 지연은 아님.
- **원인 (확정)**: 오버레이/마커 로직은 physics·playback 공통이고 둘 다 astronaut prim 원점을 투영한다. 차이는 **투영 매트릭스 획득 방식**:
  - 헤드리스 생성(`generate_episodes`) → `camera_params` annotator로 **렌더러 실제 view/projection** 사용 → 정합 정확(=이전에 "physics 때 고친" 경로).
  - 인터랙티브 Capture 버튼(`realtime_capture.py` [A2] 경로, ~388줄) → `matrices_fn` 없이 `_get_camera_matrices`로 **USD 카메라에서 재구성**(aperture/conform 추측) → 비례 오차. **playback이라서가 아니라 인터랙티브 캡처라서** 생기는 문제.
- **시도(실패, 되돌림)**: 인터랙티브 경로에 `viewport.projection`/`viewport.transform`을 직접 주입 → **더 나빠짐**. `viewport.projection`이 헤드리스의 `cameraProjection`과 다른 레이아웃(열 우선=전치, 또는 화면 뷰포트 aspect 기준)으로 추정. 커밋 안 함, 원상복구 완료.
- **다음 수 (블라인드 수정 금지)**: 한 번의 GUI 캡처로 규약을 확정하는 **진단 로그** 추가 — 한 객체에 대해 (재구성 proj) vs (`viewport.projection` 원본) vs (전치)로 각각 투영한 픽셀을 찍어 어느 게 맞는지 판명 후 확정 수정. 헤드리스 `_renderer_matrices`(`cameraViewTransform`/`cameraProjection`을 평탄·전치 없이 `Gf.Matrix4d`로)가 정답 규약의 기준.
- **임시 완화**: `TTS_OVERLAY_RADIAL_SCALE` 환경변수(기본 1.0)로 경험적 radial 보정 가능(정밀 X).
